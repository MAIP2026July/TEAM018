Does it beat a simple rule?

Each synthetic MR has an "after merge" outcome (did it need a hotfix, revert, or cause an incident). I compare two ways of picking MRs for extra review: Baseline = what many teams do informally, look harder at big MRs (more than 300 changed lines). Prototype = MRs scored High by this tool.

Read this with care. I wrote both the scoring rules and the sample MRs, so the prototype is bound to look good here. These numbers show the mechanism works end to end. They are not evidence of real-world accuracy. That needs the pilot evaluation described in 05_Data_Model_Evaluation.md.

What this prototype does and does not do

Pipeline

MR diff → feature extraction (paths, size, tests, patterns) → risk score 0-100 → band (Low / Medium / High) → reasons + suggested review path → human reviewer accepts or overrides with a reason.

Signals used

Deliberately not used

Author name, seniority or past "bad MR" history. It would probably add some predictive power, but it turns the tool into a people-scoring system and developers would stop trusting it. See the ethics note.

Honest limitations

  • The scoring is a weighted rule set that stands in for the ML model. In the pilot, the weights would be learned from real MR history (e.g. logistic regression), with these rules kept as the baseline.
  • The "AI summary" text is generated from templates here. In the pilot, an LLM would write it from the diff, with the rule signals passed in so it cannot invent reasons.
  • It has no idea about blast radius. A small change to a shared utility looks low risk (see MR-121 in the evaluation tab).
  • Keyword-based path matching over-triggers sometimes (see MR-122, a UI icon change under a "payments" folder).
